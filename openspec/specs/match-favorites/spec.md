# match-favorites Specification

## Purpose

Пользователь может независимо отмечать матчи избранными и сохранять выбор на устройстве между запусками, получая предсказуемое состояние звёздочек и понятное объяснение исправленных ошибок.

## Requirements

### Requirement: Independent favorite selection

Каждая загруженная карточка SHALL показывать доступную кнопку избранного. Выбор SHALL определяться ID матча, немедленно переключаться по нажатию и не затрагивать остальные матчи. До первого выбора при отсутствии сохранённых данных все звёздочки SHALL быть неактивны. Skeleton SHALL сохранять расположение элементов карточки без активной кнопки избранного.

#### Scenario: Initial empty favorites

- **WHEN** пользователь впервые открывает список без сохранённого избранного
- **THEN** каждая карточка имеет неактивную звёздочку с действием «Добавить в избранное»

#### Scenario: Toggle first and another match

- **WHEN** пользователь отмечает первый матч и затем другой матч
- **THEN** активны только эти две звёздочки, и каждая предлагает «Убрать из избранного»
- **AND** повторное нажатие на первую снимает выбор только с первого матча

#### Scenario: Rapid repeated toggles

- **WHEN** пользователь быстро нажимает звёздочку одного матча несколько раз
- **THEN** каждое нажатие переключает выбор, чётное число нажатий возвращает исходное состояние, нечётное меняет его
- **AND** остальные звёздочки не меняются

#### Scenario: Loading card layout

- **WHEN** список впервые загружается
- **THEN** skeleton повторяет структуру карточки с местом для звезды и не позволяет менять избранное

### Requirement: Local favorite persistence

Избранное SHALL храниться на устройстве как ID матчей без backend. Выбор SHALL восстанавливаться до первого отображения звёздочек и сохраняться при перезапуске приложения или перезагрузке страницы на том же origin. Фильтрация, прокрутка и повторное получение данных SHALL NOT сбрасывать выбор для того же ID.

#### Scenario: Restore saved selection

- **WHEN** пользователь добавил матч в избранное и перезапустил приложение либо перезагрузил страницу
- **THEN** звёздочка этого матча сразу отображается активной, а невыбранные матчи остаются неактивными

#### Scenario: Remove and restart

- **WHEN** пользователь снял ранее сохранённую звёздочку и перезапустил приложение
- **THEN** снятый выбор не восстанавливается

#### Scenario: Filter refresh and recycled rows

- **WHEN** выбранный матч скрыт фильтром или прокруткой, затем снова показан после переключения фильтра, прокрутки либо refresh
- **THEN** его звёздочка сохраняет выбор независимо от позиции и новых объектов ответа
- **AND** временное отсутствие матча в ответе не удаляет сохранённый ID

### Requirement: Local storage recovery

Отсутствующее или повреждённое сохранённое значение SHALL NOT приводить к падению экрана. Недопустимая структура SHALL давать пустое избранное, повторяющиеся строковые ID SHALL нормализоваться. При ошибке доступа к хранилищу экран SHALL оставаться рабочим с выбором в памяти и неблокирующим сообщением о невозможности гарантировать сохранение после закрытия.

#### Scenario: Invalid stored data

- **WHEN** значение отсутствует, содержит невалидный JSON, не является массивом строк или содержит дубли
- **THEN** отсутствующее и некорректное значение даёт пустое избранное, а корректные строковые дубли сводятся к одному ID
- **AND** список матчей остаётся доступным

#### Scenario: Storage read or write failure

- **WHEN** чтение или сохранение избранного завершается ошибкой доступа к storage
- **THEN** показано неблокирующее сообщение, переключение звёздочек работает в памяти текущего экрана и ошибка не подменяется ошибкой загрузки матчей

### Requirement: Explain reported defects

SOLUTION.md SHALL содержать по 1–3 предложения для каждой исходной жалобы: причину неверного состояния/переключения звёзд и причину остановки/отсутствия сброса таймера с описанием исправлений. Документ SHALL отмечать уже выполненное исправление таймера и фактические ограничения проверок без заявления о непроведённых проверках.

#### Scenario: Concise defect explanations

- **WHEN** реализация завершена
- **THEN** описание звёздочек объясняет ошибку преобразования индекса в boolean и мутацию того же массива state
- **AND** описание таймера объясняет захваченное значение счётчика, игнорирование времени успеха и отсутствие cleanup в исходном компоненте
- **AND** описаны текущие исправления и фактически выполненные проверки

### Requirement: Future favorite API contract

Контракт SHALL предусматривать одну операцию PUT /favorites/{matchId} для установки состояния избранного: обязательный matchId в пути и обязательный isFavorite:boolean в JSON-теле. true SHALL означать добавление, false — удаление; повтор запроса SHALL сохранять то же итоговое состояние. Контракт SHALL описывать success response 200 с matchId/isFavorite и error responses 400/404/500 с code/message. Этот контракт SHALL быть явно обозначен как подготовленный для будущего backend.

#### Scenario: Add and remove through one operation

- **WHEN** потребитель использует контракт установки избранного
- **THEN** один путь и метод описывают добавление при isFavorite=true и снятие выбора при isFavorite=false
- **AND** обязательные входные поля, успешный ответ и ошибки описаны переиспользуемыми схемами

#### Scenario: Generated API remains unused by local feature

- **WHEN** контракт обработан генератором и пользователь нажимает звёздочку в тестовом приложении
- **THEN** generated Fetch-метод и mutation hook доступны через публичный API пакета, но UI обновляет только локальное избранное без HTTP mutation
- **AND** в компоненте есть комментарий о доступном generated hook, отсутствии backend и временном использовании localStorage
